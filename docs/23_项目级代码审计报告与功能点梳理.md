## 4. 安全审计（重点）⚠️

### 4.1 根因：鉴权门控默认关闭 → 信任自报角色（高危，已确认）
- `core/config.py:112`：`staff_auth_enabled: bool = False`。
- `core/rbac/__init__.py:45-60`：门控关闭时退化为 `if not any(role in actor.roles ...)`——**完全信任请求体自报 `roles`**。
- 含义：当 `staff_auth_enabled=False`（当前默认），任何写请求只要 body 里写 `"roles": ["operations"]` 即可通过 `require_any_role` 校验。这是"任何人可伪造运营角色"的系统性风险。
- 缓解现状：仅 `mcp/router.py:39`、`a2a/router.py:74` 走真 Bearer + SHA-256 验签；其余 staff 端点依赖关闭的门控。

### 4.2 五处写口绕过 `require_any_role`，自判角色（高危，已确认）
下列 service 内部自判 `actor.roles` 或 `_require_ops/_require_owner/_require_role` **不触达** `require_any_role`，故永不校验 staff PAT：

| atom Gate | `product/atom/service.py:335,415,437,582,623,680-682,749` | `router.py:208` approve / `:227` batch-approve / `:246` reject / `:304` cluster-resolve / `:325` risk-override / `:348-462` freeze/unfreeze/suspend/resume/deprecate/archive/reject |
| 段9/10 策略包 | `decision/layer_strategy/service.py:49-51` | `router.py:49,71,87` create/update/archive |
| ~~段11 终稿白名单~~ | ~~`final/final_whitelist/service.py:102-104`~~ | ~~该模块全部写口~~ **〔订正 2026-10-01：此条不成立，见 §4.2 订正〕** |

**修法与取证**：8 口按其路由实际使用的 gate 补入 `GATED`（全部是 `require_internal_actor(OPERATIONS)` ⇒ 期望角色 `operations`）。补完 `pytest tests/integration/test_write_gate_wiring.py`＝**2 passed**；再**种植缺陷证明它能红**——摘掉 `app/platform/platform_adaptation/router.py:320` 的 `verified: Actor = Depends(_ops_gate),`，`test_every_gated_write_route_carries_the_credential_dependency` 当场判红（`AssertionError … 0 = len([])`，报错直指该路由），随后按 `sha256sum -c` 断言文件**字节还原**并重跑回绿。收集数不变（该测试不参数化，2 例）。

> **可复发的根因**：`GATED` 是**手工清单**，而新写口按批持续增长（Q249／Q250／Q259 三批共 8 口无人补）。可选收口方案（**须点工，本批不擅自改**）＝在守卫里加一条**反向枚举断言**：遍历 `app.routes`，凡依赖闭包带 `loom_requires_internal_credential` 标记的路由必须出现在 `GATED` 中——把"清单是否完备"从人工纪律变成机器判据。

### 11.4 新增结构性发现：授权判定有**四种写法**（P2）

同一个问题"这个调用者能不能做这件事"在仓内有四套表达，本批实测分布：

| 机制 | 位置与数量 | 是否校验凭证 |
|---|---|---|
| `rbac.require_any_role` | **68 个调用点**（服务层为主） | 门控开时用已验真身份覆盖自报；**门控关时信任自报 roles** |
| `require_internal_actor(ROLES)` 路由依赖 | **10 个 gate 对象覆盖 38 个写口**，闭包上留 `loom_requires_internal_credential` 标记 | **两种门控态下都验真**（Q203／Q242） |
| 模块内局部 helper（`_require_ops`／`_require_owner`） | platform 15／fcw 4／layer_strategy 2／whitelist_center 2 调用点 | 只看 `actor.roles` 成员，不验凭证 |
| 裸成员判断 `X not in actor.roles`／`set(actor.roles) & {…}` | compliance_wordlist `:63,98,131`／config_center `:30`／atom `:335,415,437,582,623`／condition `:153,658,678`／layer_strategy `:262` | 只看 `actor.roles` 成员，不验凭证 |

**后果不是"哪个口不安全"，而是没人能用一条命令回答"受闸面全貌是什么"**——§11.2 的漏钉正是这样产生的：Q242 只统一了 grep 得到的那一类。建议（须点工）＝把后两类收敛到 `require_any_role`，或在 `rbac` 提供一个可被守卫枚举的**唯一标记**，使"受闸写口"成为可机读集合。
