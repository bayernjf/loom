# 27 — 立项差距与待办（2026-11-23，本地自用口径）

> 性质：一次性审计 + 待办台账，不是契约、不是排期承诺，也不替代 `docs/24`、`docs/25`、`docs/02`。
> 口径：只算「本机单人自用」真正影响使用的差距。公网自助、多租户、客户计费、SLA、正式客户成功体系不算硬缺口，只列为后置项。
> 2026-11-23 追加口径：对外开放、上线、生产相关任务一律不作为阻塞项；P0/P1/P2 只按本机自用跑通与效益排序，外部投递/公网接入只作可行性观察。
> 2026-11-23 追加约束：现有功能全部保留，只做追加式迭代；不删除、不替换、不回退当前已有能力。当前功能即使与原立项不同，也视为需要保留的产品资产；“对齐”只补缺口，不做破坏性重构。当前 private beta、客户菜单、`loom_client_`/`loom_staff_` 模式均在保留范围内。
> 事实源优先级：条级看 `docs/25_PRD逐条验收台账.md`，段级看 `docs/24_功能点比对_ContentOS产品基准.md`，当前批次看 `handoff.md`。三者粒度不同，不做简单相加。
> 结论时点：2026-11-23。测试数字引用 2026-11-22（Q376）的既有快照，本轮未重跑全量测试。

## 0. 一句话结论

- **核心产品定位没有偏**：仍然是同一条 13 段主链、同一个 `final_id` 六层快照、同一个唯一出口 `E1.1 publishFCW`、同一套人工 Gate。
- **偏的是商业形态和完成深度**：原立项是「私域内容生产白名单 SaaS 后台」，现在是 `Q144` 裁决后的「受控 private beta / 平台代运营」；客户数为 0，客户侧没有登录页，客户内容口用 `loom_client_` Bearer，运营写口用 `loom_staff_` 个人令牌。
- **原 V1 主链已经达标，不是「V1 没做完」**：V1 范围 41/41 条 ✅，主链 `1→6→10→11` 已闭合。当前真正没完成的是 V1 之外的厚度：13 段中段 3/7/9/12 仍为部分闭环，以及「一个真实自有产品从入料到反馈回流的全链 dogfood」。
- 一句话：**Loom 已经不是「能不能跑通」的问题，而是「愿不愿意用一个真实产品把它跑脏、把 V2 厚度补齐」的问题。**
- 本轮不是回退到原立项的公网 SaaS：当前 private beta、客户菜单、`loom_client_`/`loom_staff_` 模式全部保留；对齐只追加 V2 厚度和真实 dogfood。

### 1.1 关键结论

1. **V1 主链不是缺口**。`docs/25` 明确记录 V1 主链 41/41 ✅；把「13 段中 4 段部分」直接说成「V1 没做完」是不准确的。
2. **当前缺口主要在 V2 厚度**。段 3/7/9/12 的部分闭环，加上 Q41、Q44、Q59、Q63–Q65 这些条级缺口，基本都落在 V2 或 V1 之外的增强项。
3. **真实业务 dogfood 是最大空白**。当前客户数为 0，真实 C1 intake 只到候选生成，尚未用一个真实自有产品把 13 段全链跑穿。原 handoff 写「真实客户 dogfood blocked」；在本地自用口径下应改判为「真实自有产品 dogfood」，不要求外部客户。
4. **合规与客服体系是主动后置，不是漏做**。公网、多租户、计费、SLA、客户成功在原立项里属于 V2/V3；当前 Q144 已明确不走公网自助，所以这些不能算本地自用的硬缺口。
