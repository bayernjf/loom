## 2. 现状盘点（回源码实测，2026-10-10，head=0054）

### 2.1 已落的「各自为政」回滚/版本机制（五套，互不相通）

- **配置中心版本化**：`config_items`＋`config_item_versions`（uq(key,version)，历史 append-only）；发布＝新版本＋`config.update` 审计；**回滚已实现**＝以新版本重发历史值（`config.rollback` 审计，PUT/rollback 均 platform_admin）＋after_commit 进程内快照原子切换。
- **PWS 快照**：`pws_snapshots`＋`pws_snapshot_items`＋`pws_freeze_logs`；版本 v1.0…vN.0 全保留、同刻仅 1 active；Q29 重冻三档、Q30 换版四行处置、Q32 `revoked` 急停（作废后可重冻新版）——**撤销靠「作废＋重冻」，没有「回到旧版」**（Q30：已发布不追溯）。
- **FCW 快照**：`fcw_snapshots`＋`fcw_freeze_logs`（Q250）；`POST /api/admin/fcw/{final_id}/revoke`（operations 闸）；复用＝走 E1.1 再发证——同样**只支持作废＋新发，不支持 restore**。
- **合规词库**：词条 CRUD＋Q51 生效即扫（联动强制重冻待办）；词表本身无版本回滚。
- **SkillRunLog / audit**：全链 append-only，PT-COMPLIANCE-V2.0 明写「历史 SkillRunLog 不可 mutate（即便回滚）」。

### 2.2 真缺口

- **无统一回滚登记处**：五套机制各有自己的撤销语义（新版本重发/作废重冻/revoke/无），运营没有一个面能回答「昨天改了什么、哪笔能撤、撤了影响谁」。
- **Skill/Prompt 回滚没有载体**：模型注册表（场景→Prompt 版本）有版本概念但无「回滚到上一版」的操作面。
- **Q63 的 KUP 回滚点**：KUP-PROPOSE 随 V2 未落，回滚点机制连触发方都没有。

## 3. 候选方案

### 3.1 第一刀范围

- **甲（推荐）＝只读「变更-回滚清单」聚合面**：新建统一读口（如 `GET /api/admin/change-ledger`）把五套机制的变更事件（config.update/rollback、PWS freeze/revoke、FCW issued/revoke、词库 CRUD、Skill/Prompt 版本发布）**按时间与影响面聚合**；每笔标「可回滚性」（能撤/只能作废重发/不可撤）＋**一跳直达既有操作面**（配置回滚口/PWS 重冻/FCW revoke）。零新业务语义、零新迁移（纯读既有审计与版本表）。理由：先把「能看什么」做全，回滚动作复用各机制已裁决的既有口，不发明第六套语义。
- **乙＝甲＋Prompt/Skill 版本回滚操作面**：给模型注册表补「回滚到上一 Prompt 版本」写口（新发布＝以历史 Prompt 内容发新版本，照配置中心先例，不 mutate 历史），触发 Q49 式人工 Gate。依赖：注册表当前 Prompt 版本字段盘点（落码前实测）。
- **丙＝通用快照-恢复服务**：为任意实体提供 point-in-time restore；与 Q30「已发布不追溯」、PT「SkillRunLog 不可 mutate」存在口径冲突，须先由负责人裁决「restore 是否允许产生『看起来没发生过』的状态」，风险最高，不推荐。

### 3.2 聚合面的载体

- **甲-1（推荐）＝派生读，不落新表**：从 `audit_log` ＋各版本表现查聚合；优点＝零迁移、天然不漏；缺点＝性能须实测（分页＋按 entity 过滤索引盘点）。
- **甲-2＝物化投影表**：新表按事件投影，查询快但多一个写路径要维护一致性。
